## Findings

### NEW-H1 (High): the function denylist is bypassed because sqlglot uppercases function names with Unicode rules
- **What:** guard 5 compares `name.lower()` with `_FORBIDDEN_FUNCTIONS`. The guard then returns `statement.sql(dialect="duckdb")`, and sqlglot's generator runs `normalize_func` → `name.upper()` (`.venv/.../sqlglot/generator.py:1088-1090`; DuckDB's `NORMALIZE_FUNCTIONS = "upper"`, `dialect.py:404`). In Python, `'ı'.upper() == 'I'`, `'ſ'.upper() == 'S'` and `'ﬆ'.upper() == 'ST'`. A name the guard sees as unknown therefore comes out as a forbidden ASCII name. This is the reverse of HIGH 1: the earlier problem was Unicode *lowering* in the guard, this one is Unicode *uppercasing* in the SQL generator.
- **Where:** `api/services/warehouse_tools.py`, the loop over `statement.find_all(exp.Func)` (`name.lower() in _FORBIDDEN_FUNCTIONS`) and `return statement.sql(dialect="duckdb")`.
- **Evidence** (temporary DuckDB under /tmp, run through `query_marts`):
  ```
  BYPASS "SELECT current_settıng('secret_directory') ..." -> SELECT CURRENT_SETTING('secret_directory') ... [['/home/ellie/.duckdb/stored_secrets']]
  BYPASS "SELECT current_ſetting('home_directory') ..."   -> SELECT CURRENT_SETTING('home_directory') ...
  BYPASS 'SELECT pg_get_vıewdef(1506) ...'                -> SELECT PG_GET_VIEWDEF(1506) ...   (ran; returned NULL for my oid)
  BYPASS 'SELECT pg_get_conﬆraintdef(1, true) ...'        -> SELECT PG_GET_CONSTRAINTDEF(1, TRUE) ...
  BYPASS 'SELECT get_block_ſize(current_database()) ...'  -> SELECT GET_BLOCK_SIZE(CURRENT_DATABASE()) ... [[262144]]
  BYPASS 'SELECT "current_settıng"(...)'                  -> SELECT "CURRENT_SETTING"(...) [['/home/ellie/.duckdb/stored_secrets']]
  ```
  The quoted form is uppercased too. The only one refused was the method-call form `('x').current_settıng()`, and that was by the engine (`query_failed`), not the guard.
- **Characters involved:** an exhaustive scan of all code points finds 10 non-ASCII characters whose `upper()` is ASCII: U+00DF ß, U+0131 ı, U+017F ſ, and U+FB00 to U+FB06 (ﬀ ﬁ ﬂ ﬃ ﬄ ﬅ ﬆ). Every name in `_FORBIDDEN_FUNCTIONS` can be reached with at least one of them.
- **Impact:** a prompt-injected agent can read the OS username and home path through `current_setting`. On the phase-10 evidence it can also read the SQL of views outside the allowlist through `pg_get_viewdef`. This is exactly the leak ADR-012 says is closed. This was not introduced by this delta (guard 5 came in 4ac9ed8 on the same branch). The new ADR paragraph says the call shapes the engine executes are "pinned as refusals", which is not true for this one.
- **Fix:**
  1. Refuse any non-ASCII function name, the same way `_fold` does for tables: `if not name.isascii(): raise ToolError("function_not_allowed", ...)`.
  2. Defence in depth that closes the whole class of differences between what the guard checks and what runs: re-parse the emitted `safe_sql` and run the same checks on it. Equivalently, require `guard_select(safe_sql) == safe_sql`, or at least compare the multiset of function and table names before and after generation. Optionally also generate with `normalize_functions=False`.
  3. Add the six BYPASS strings above to `test_catalogue_and_configuration_functions_are_refused`, so they fail before the fix.
- **Effort:** S (about 10 lines plus the test cases).

## Probes that did not break the new folding (proof that nothing was found)
I ran these on a temporary DuckDB 0.10.2 database under /tmp with sqlglot 30.18.0, with the guard first and the engine behind it.
- **Quoted vs unquoted case for CTE vs table:** `WITH "STG_SECRET" ... FROM stg_secret`, `WITH stg_secret ... FROM "STG_SECRET"` and mixed case all return the CTE (`[(1,)]`). DuckDB matches case-insensitively both ways, the same as the guard's fold, so the real table is never read.
- **Non-ASCII schema:** `"maiın".dim_track` is refused as non-ASCII. `"MAIN".dim_track` passes and reads main, which is correct. `s2.dim_track` is refused. `"s2.dim_track"` (dot inside the quotes) is refused.
- **Look-alike characters in table names:** zero-width space and fullwidth `ｄim_track` are refused by the guard, and DuckDB does not fold them either.
- **Function names that DuckDB itself might fold:** fullwidth `ｃurrent_setting`, `pg_get_viewdeｆ` and `CURRENT_SETTİNG` (U+0130) pass the guard but fail in DuckDB with `Scalar Function ... does not exist`. DuckDB does not fold them; only sqlglot's `upper()` creates the bypass in NEW-H1.
- **Kelvin inside a function name:** `get_blocK_size` is refused by the guard, because Python's lower() turns it into the forbidden name. It is over-refused, which is harmless.
- **`U&"..."` Unicode escapes:** sqlglot raises a parse error, so the guard refuses them.
- **Empty schema:** `"".dim_track` passes the guard, but DuckDB fails to parse it ("zero-length delimited identifier"). No leak.
- **NUL byte or trailing backslash in an identifier:** refused or erroring.
- **Comment break-out:** `-- */ UNION ALL SELECT ... FROM stg_secret /*`. sqlglot rewrites `*/` inside comments as `* /`, so the emitted SQL keeps the injection inside the comment and the engine returns only `dim_track` rows.
- **Identifier normalisation by sqlglot:** `identifier_sql` (generator.py:2015-2029) lowercases only when `normalize=True`, and the default is `False` (l.900). The guard therefore sees the same table identifiers that are emitted.
