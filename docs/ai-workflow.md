## Session 2026-08-19 — Cross-cutting — Make the phase-2 `pipeline` profile actually come up: the Airflow UI 500, and host ports that survive other local stacks

**Loop**: reproduce → separate the visible failure from the blocking one → root-cause in the installed package, not by guessing → fix → verify each endpoint → owner rejects the first port doctrine → rewrite → verify again
**Tool/model**: Claude Code / Opus
**Initial prompt**: (owner, in French) pasted terminal output of `docker compose --profile pipeline up` failing, then "comment le faire fonctionner ?". The E.5 exit criterion — the 3 DAGs green in the Airflow UI — is the human step phase 2 left open, and it could not be reached.
**Notable iterations**:
- **The error on screen was not the one blocking the phase.** `Bind for 0.0.0.0:8000 failed: port is already allocated` is real, but 8000 was held by an unrelated stack on the machine (`weather-mlops-api-1`, up 36 h), not by CycleBeat — and `--profile pipeline` starts the profile-less services (`api`, `prometheus`, `grafana`) *in addition to* `airflow`, so a collision on any one of them kills the whole foreground `up`. Starting Airflow alone got past it, and that is when the actual defect appeared: **every** UI and API route answered `500`.
- **The 500 was root-caused in the installed source, not inferred from the traceback.** Airflow 3.0.6 + PyJWT 2.13: `JWTGenerator.issuer` is built by `_conf_list_factory("api_auth", "jwt_issuer", first_only=True, fallback=None)`, which yields `[]` — and the `[] -> None` converter that would fix it exists only on the token *validator* class, not on the generator. `generate()` then drops `iss` only when it `is None`, so PyJWT receives `iss: []` and raises `TypeError: Issuer (iss) must be a string.`. Confirmed by instantiating the generator inside the container both ways: `repr(g.issuer)` is `[]` unset, `'cyclebeat'` with `AIRFLOW__API_AUTH__JWT_ISSUER` set, and a token is produced. `SIMPLE_AUTH_MANAGER_ALL_ADMINS=true` routes every request through that generator, which is why the whole UI was down rather than just login.
- **A tempting follow-up fix was identified as a trap and written into the compose file as a warning.** Setting `AIRFLOW__API__BASE_URL` to match a shifted host port looks right, but the task SDK derives `[core] execution_api_server_url` from it; inside the container nothing listens on the host port, so the UI would look correct and every task run would fail. The default (`localhost:8080`, container-side truth) is kept, with the reason in a comment so it is not "fixed" later.
- **The first port design was rejected by the owner and rewritten.** The initial fix reserved a private contiguous block (8084-8087) for the project. The owner asked instead for each service to keep its conventional port (8000 / 8080 / 9090 / 3000) and to step to the next free one only when that one is taken. `tools/compose_ports.py` now probes upward from each default and execs the compose command with `CYCLEBEAT_*_PORT` injected. Two design points that mattered: it asks **Docker**, not just `bind()`, because the owner runs compose from WSL while Docker Desktop publishes on the Windows host, so a bind probe inside WSL would declare 8000 free; and it **excludes containers of the `cyclebeat` project**, otherwise a container being recreated would still hold its port and every service would drift up one slot per restart. Idempotency checked by running the picker twice with the stack up.
- **`uv run` from WSL destroyed the Windows virtualenv, and the compose targets were decoupled from it.** The owner's `make compose-pipeline` died with `failed to remove directory .venv/Scripts: Input/output error (os error 5)` — uv saw a Windows-layout venv, tried to recreate it POSIX-style over the `/mnt/c` drvfs mount, and had already deleted `.venv/Lib` before failing. Repaired by re-running `uv sync` from Windows (178 packages). `tools/compose_ports.py` imports nothing outside the standard library, so the Makefile runs it with a bare interpreter rather than through `uv run`, which removes the failure mode entirely for these targets.
- **The inherited healthcheck was fixed for what it was.** `airflow`, `ingest` and `dbt` all build from the API image, whose `HEALTHCHECK` curls `:8000/health`; none of them runs uvicorn, so the probe could only ever fail — hence `Up 14 hours (unhealthy)`. Disabled per-service. Checked first that nothing depended on it: the `depends_on` chains key off `service_completed_successfully` (exit code), not health.
**Corrected by human review**: the owner rejected the private 8084-8087 block in favour of conventional defaults with upward fallback — the version that ships; and chose `docs/ai-workflow.md` over `docs-notes/` for this entry when asked (`docs-notes/*` is gitignored bar an allowlist, so an entry there would not have been committed).
**Role split**: decided by the human: the port doctrine (conventional first, step up only on collision), the location of this entry / delegated: the diagnosis of both failures, the `jwt_issuer` fix, `tools/compose_ports.py`, the Makefile targets, the healthcheck cleanup, the README port section, this entry.
**Verification**: `uv run ruff check api cyclebeat dags db ingest tests tools` clean. `docker compose config` valid. Full stack recreated and every endpoint probed: API `:8001/health` → 200 and container `(healthy)`, Airflow `:8080/` → 200, Prometheus `:9090/-/ready` → 200, Grafana `:3001/api/health` → 200 — 8080 and 9090 kept their conventional value because they were free, 8000 and 3000 stepped up one because another stack held them. `airflow dags list` inside the container lists the 3 DAGs (`dag_ingest`, `dag_resolve_bpm`, `dag_build_warehouse`). **Spec/actual gaps**: `make` is absent from the Windows shell used here, so every target was run through its exact underlying command; **the WSL `make compose-pipeline` fix is therefore unverified from WSL itself** and needs the owner to re-run it. The E.5 human step (3 DAGs green in the UI) is now reachable but still the owner's to confirm — the DAGs load and are listed, they are not unpaused or run here. **Lesson**: the loudest error in the output was not the blocking one. `port is already allocated` was true, self-explanatory, and would have been "fixed" by freeing 8000 — leaving a stack whose Airflow UI 500s on every route, which is exactly the criterion the phase needed.
